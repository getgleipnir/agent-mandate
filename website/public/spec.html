The mandate specification

A mandate is a power of attorney for an AI agent: a person who may sign for a company states what one agent may pay, from which accounts, to whom, how much and until when. A bank or PSP checks it before executing a transfer the agent started, and records a signed decision.

  "company": { "name": "Nordhafen Logistik GmbH" },

  "agent": { "id": "ap-agent", "jkt": "aVBtapLd…" },

  "scope": { "max_per_payment": "500.00",

    "counterparties": ["shop.example.com"] },

  "sig": { "type": "webauthn", … } }

A mandate, shortened.

Scope of this version

0.6 is written for company payments, with a profile for agent protocols in section 14: agent key binding, counterparties as domains, principals without user data, per-operation approval and Token Status List. Use by consumers and for other actions is open work. The experimental mandate link is a separate prototype.

Objects

  • Mandate: company, agent, signer(s), from accounts, payees, rails, currency, per-payment and per-period limits, validity. Signed by the company signatory (passkey/WebAuthn, Ed25519 or ECDSA P-256), alone or jointly.
  • Payment: the transfer the agent wants to make, bound to the mandate by hash and signed by the agent.
  • Decision: allow, block or escalate, the checks that passed, reason codes, signed by the bank’s checker.
  • Revocation, signed status and revocation lists: withdrawing a mandate, effective from the next check.
  • Override: a person signs a decision on an escalated payment.
  • Delegation: authority passed down a chain, never wider than its source.

Where trust comes from

Only from the bank’s own records (its KYB and the keys it enrolled for each signatory) or a vLEI credential, never from the mandate. After that, every link is a signature.

The check

Ordered steps in five groups: parse, authentic, authorised, still valid, in scope. Each yields a reason code such as payee_not_on_mandate, mandate_revoked or over_payment_limit. The checker uses its own clock, keeps an idempotent payment log, reserves period limits atomically and fails closed.

Encoding and interoperability

  • RFC 8785 (JCS) canonical JSON, SHA-256, Ed25519 or ECDSA P-256, base64url without padding, strict RFC 3339 timestamps.
  • Closed object shapes; extensions only under x. Lengths fit ISO 20022.
  • ISO 20022 pain.001.001.09 mapping with the mandate, payment and decision hashes in SplmtryData.
  • Bank checker keys published at /.well-known/gleipnir-checker.json.

Conformance

A Python reference and a TypeScript port pass the same published test vectors and verify each other’s decisions. The vectors cover multi-signature, joint signing, delegation, cross-bank vLEI, passkey assertions, eight account schemes, signed status, overrides, key rotation and ISO 20022 messages.
