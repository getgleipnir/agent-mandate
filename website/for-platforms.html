For teams building agents

Your agent gets stopped because nobody can tell who sent it. Limits inside your own product don’t help once the agent leaves it.

What you get

Your customer signs one mandate for one agent with a passkey. The agent carries it to the bank, supplier or company it deals with, and that side can check it without calling you.

Your customer can revoke it, and you stop writing separate rules for every counterparty.

For payments

The agent signs each payment with its own key and attaches the mandate. The bank’s checker decides. There are worked examples for Stripe Treasury and Increase on GitHub, and an MCP server so an agent can use it as a tool.

For agent protocols

Spec 0.6 adds a profile for protocols where an agent proves its own key on each request:

  • the agent is bound by key thumbprint
  • counterparties are named as domains
  • no personal data in what the operator relays
  • the person approves a single operation with a passkey
  • revocation through a Token Status List

It is a draft written around payments. Other actions are open work, and we want to do them with real teams.

What it does not do

It proves who allowed what. It does not catch a bad decision inside the allowed scope, or a prompt injection that stays within it. And a counterparty has to choose to check it, which most don’t do yet.
